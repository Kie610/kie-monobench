# 自作CAD・CAM 計画と設計

この文書は、`policy.md` の決定を前提にした、段階計画・モジュール境界・コア API・検証方針の今効く決まりを置く。**新しい機能の記録と決めたことは、このファイルに足さず docs/機能/ の断片に書く**(docs/機能/README.md。ここへ足すと PR どうしが同じ所で衝突するため、2026-10-21 Kie)。

確定度の記号: **C** = 出典で確認済み、**A** = 仮定(提案者の判断・推測)、**U** = 未解決。

## 目的

policy.md の「未決事項」のうち、段階計画と検証方法を具体化する。あわせて、policy.md の「構造の考え方」を crate 単位の境界と、コアが公開する API の形に落とす。

## 範囲

この文書が扱うのは、policy.md の「最初に作るもの」(スケッチと拘束、パラメータと式、タイムライン型ソリッド、CAM のセットアップ・ストック・工具・加工操作、Carvera Air 向け G-code)までである。「当面作らないもの」には触れない。

### 実装の条件(Kie のメモ)

- タブと版(段 1): モデル管理の機能も、版の管理と一緒に作る。モデル管理だけの既存製品があるので調べてから作る。フォルダの構造だけでなく、タグ・ジャンル・プロジェクト名などでも分類できるようにする(決定: モデル管理と分類)。
- 絵と動画(段 3): 動画は MP4 などにも対応する。H.264 の符号器はアプリに入れず、Windows は OS の H.264、ほかは AV1 で書く(docs/避ける形.md「絵と動画」)。
- 文字(13): 既定の書体は 1 本線でなく、Windows に元から入っている一般的なゴシック体にする(Kie 2026-10-19。PC に入っている書体を読むだけで、アプリには同梱しない)。1 本線の文字は彫刻向けに選べるまま残す。アプリの画面のフォントも選べるようにする(決定: 文字の既定の書体)。
- レーザー(7)は Carvera Air に寄せない汎用のレーザー加工として作る。板への配置(41)は作業範囲か材料の大きさを設定して敷き詰め、はみ出しは注意だけ。区切って削る(42)とはめ込みの枠(47)は、捨て板に開けた穴に位置決めピンを差す仕組みを共有する(表裏の両面加工にも使う)。平歯車(46)は設計の機能として置く。写真のような静止画(23c)は docs/避ける形.md「絵と動画」の方式を使わない。工具が届かない所を色で見る(6)は 2026-12-08 の特許の満了の後に作る。

- 加工の汎用化の洗い出しの例(2026-10-19 にコードを読んで確認): 作業座標を G54 だけと知らせる(kmb-cam-setup)、穴あけで固定サイクルを使わない(kmb-strategy-drill)、荒削りの 1 段の深さの既定が Carvera Air の条件(kmb-strategy-adaptive2d)、最初の工具が Carvera Air の付属工具(kmb-cam-tool の carvera.rs)。機械ごとの値はマシンライブラリとポストへ移し、Carvera Air の値はその既定値として残す。汎用化は 中 なので、加工の高さと空振り(高)は今の作りの上に先に作る。

## 構造の考え方

### crate の分け方

接頭辞は `kmb-` とする(2026-10-25 Kie、policy.md「決めたこと」の製品名)。依存の向きは上から下のみで、`kmb-core` が依存するのは `kmb-expr` だけにする。

crate の一覧と役割は docs/地図.md「crate の役割」にある(`cargo xtask docs` が各 Cargo.toml の `description` と層から作る)。加工戦略の crate は加工の種類のまとまり(2D・穴・3D・彫刻など。レーザーは分ける)で、差し替えの単位は crate でなく戦略の名乗り(`module()` が登録する 1 戦略)とする(2026-10-21 Kie、構造のレビューの判断 2)。

戦略は形状カーネルに直接触らず、ホストが解いた入力 `StrategyInput`(`kmb-cam-geom` の輪郭・網などの加工用の幾何を含む)だけを受け取る(policy.md「構造の考え方」)。こうすると、WASM プラグインの戦略にもカーネルのハンドルを渡さずに済み、truck を将来入れ替えても戦略は変わらない。

### コア API の考え方

方針の柱は二つある(A)。

1. **文書モデルは純データ、形状は派生キャッシュ。** 文書に保存するのは機能の種類・パラメータ・参照だけで、形状は再計算で作り直す。取り消しは文書モデルの差分を戻すだけで済み、保存ファイルも小さく差分を取りやすい。
2. **CAD と CAM の操作を同じ `Feature` として扱う。** policy.md の「CAM もタイムラインに載せる」を、型のレベルで保証する。

今の型は kmb-core の rustdoc(`cargo doc -p kmb-core`)と各ファイルの `//!` を見る。

コア API の版 `CORE_API_VERSION` は公開まで上げない(2026-10-21 Kie、構造のレビューの判断 3)。PR ごとに上げると版の 1 行が毎回衝突するうえ、どこからも読まれていなかった。代わりに `cargo xtask verify` が kmb-core の公開の項目の一覧(`cargo xtask api` で見られる)を分かれ目と比べ、変わっていれば契約テスト(kmb-contract)を使う crate を全部選んで流す。

操作(`Action`)は受け取る引数を `Action::args` で宣言する(鍵・型・単位・既定・必須。kmb-core の `args`。2026-10-22、構造のレビューの段 1)。`Extensions::run` は実行の前に宣言で確かめ、知らない鍵・型の違い・無い必須の引数を誤りにし、`"0.5 in"` のような単位つきの式を宣言の単位の数(長さは mm、角度は deg)に直し、省いた引数に既定を入れる。操作は引数を `cx.arg`・`cx.arg_f64`・`cx.arg_str` で読み(`cx.args.get` を直に呼ぶと `cargo xtask checks` の層の点検が落とす)、宣言に無い鍵を読むと debug の組み立てでは誤りになる(試験で足し忘れを捕まえる)。既定は宣言と読む所で同じ定数を使う。一覧に出さない操作(画面の部品が中から呼ぶ物)は `Extension::unlisted` で宣言し、宣言が無ければ引数を受け取らない(段の帯の段のように値を ID の後ろに付ける物)。`Input::Name` の操作は画面が渡す `name`・`selection` を自動で受け取る。画面が全部の書き出しに渡す引数(隠したボディ・視点・時刻)は、宣言した操作にだけ渡す。CLI の `kmb actions`・`kmb run`、コマンド欄の `actions`・`run`、MCP の `actions`・`run_action`・`app` の `run` は、この宣言から一覧を出し、同じ確かめを通る。画面の無い道(`Headless::run`)とコマンド欄の `run` は、使えない操作(`disabled`)を理由つきで断る。CLI・MCP でセットアップを省いた時は、呼ぶ側が初めのセットアップを選んでから渡す(`Headless::first_setup`)。MCP のまとめて実行(`batch`)は、パラメータと機能の値を直す手が続く間は形の作り直しを後へ回し(`Headless::hold_recompute`)、ほかの手の前と最後に 1 回だけ作り直す(決定: まとめて実行の作り直しを 1 回に)。

文書のうちタイムラインに乗らない中身(モーション スタディ・接触セット・レンダリングのシーンなど)は、それを扱うモジュールが名乗る区画(`kmb_core::SectionType`。鍵・版・移し方)に置き、汎用の変更 `Op::SetSection` で書く。知らない区画と区画の中の知らない項目は書き戻す(2026-10-23 構造のレビュー段 3、保存形式 版 4)。レンダリングのシーンの設定は文書ごとに区画へ保存し、区画の無い文書と新しい文書は前回使った設定にする(決定: シーンの設定を文書ごと)。アニメーションの段(`asm.animation`)・構成表(`config.table`)・ボディの材料(`cad.materials`)・外観(`render.appearances`。ボディ・部品・面の外観と「このデザイン内」の外観)も区画に置く(保存形式 版 5)。材料と外観の表、光源とデカールの型は、描き手(inspect)と解析も引くので、コアの層の小部品 kmb-look に置く。残り: ボディに長く使える ID(最初に作った機能とその中の番号)を付けて「今の最後の機能」を再計算の派生物にする。

画面の無い道の誤りは種類つき(kmb-core の `Problem`・`ProblemKind`: 入力・計算・見つけた問題・使えない・ファイル。2026-10-22、段 1b)。拡張点の操作は今も文字列で返し、種類は入り口(`Headless::run`・`load`・`write_output`・CLI)で決める。CLI は種類で終了の番号を分け(1 入力・2 再計算の誤り・3 確かめで問題を見つけた・4 使えない・5 ファイル)、MCP は誤りの答えの structuredContent に `kind` を入れる。書き出しは画面・CLI・MCP・Headless とも `kmb_session::write_output`(壊れない書き込みとログ)を通し、画面とアプリの層で `fs::write` を直に呼ぶと層の点検が落とす。

再計算は次の規則で行う(A)。

- 機能はタイムラインで自分より前の出力しか参照できない。依存は有向非巡回グラフになり、変更された入力から下流だけを再計算する。入力のハッシュが変わらない機能はキャッシュを使う。
- 機能の失敗は文書全体を止めない。失敗した機能と、その下流を「エラー」として表示し、理由を `RecomputeReport` に入れる。
- カーネルや機能の panic は、再計算(kmb-core の recompute)が機能ごとに `catch_unwind` で捕まえて、その機能の誤りにする。truck のカーネルは呼び出しごとにも捕まえ(lib.rs の `guard`)、再計算の外からの呼び出し(加工・表示の網・書き出し・別スレッドの STEP の読み込み)でも panic をどの操作かの付いた誤りにする。時間制限は truck の STEP の読み込みにだけ掛ける。

参照の永続化は「生成履歴による名前付け」を使う(A)。各機能は、作った面と稜線に、入力から決まる名前(スケッチ要素の ID と、上面・側面などの役割)を付けて返す。再計算後は名前で探し、見つからない・複数ある場合は `hint` で絞り、それでも決まらなければ参照切れとして止める。黙って別の面に付け替えることはしない。

### 経路の中間表現とポスト

```rust
// kmb-toolpath(単位は mm と mm/min に固定)
pub enum Op {
    Rapid { to: P3 },
    Linear { to: P3, feed: f64 },
    Arc { to: P3, center: P3, plane: Plane, dir: ArcDir, feed: f64 },
    ToolChange { tool: ToolId },
    Spindle { rpm: f64, dir: SpinDir },  // Stop を含む
    Dwell { seconds: f64 },
    Comment(String),
}
pub struct Program { pub wcs: WcsId, pub ops: Vec<Op>, pub tools: ToolTable }

// kmb-post
pub trait Post {
    fn id(&self) -> &str;
    fn check(&self, p: &Program, m: &MachineProfile) -> Vec<Diagnostic>; // 範囲・回転数の検査
    fn emit(&self, p: &Program, m: &MachineProfile) -> Result<String, PostError>;
}
```

ポストは中間表現を文字列にするだけで、経路を変えない。可動範囲、主軸回転数の上限、工具番号の範囲は `MachineProfile` に持たせ、`check` で出力前に検査する。Carvera Air の値は次のとおり。

| 項目 | 値 | 確定度 |
| --- | --- | --- |
| 作業範囲 | X300 × Y200 × Z130 mm | C(機械の公表値) |
| 主軸 | 200 W、0〜13,000 rpm、閉ループ制御 | C(同上) |
| 工具交換 | レバー式のクイックツールチェンジ(手動) | C(同上) |
| 単位 | mm で出力(G21) | C(policy.md) |
| 工具交換の指示 | `T<n> M6` | C(policy.md) |
| 手動交換後の工具長の再測定 | 純正ファームの文書では未確認 | U。P3 の空運転で実機確認する |
| コレット径 | 未確認 | U。工具ライブラリの既定値に必要 |

ほかのポストのコードは参照しない。出力の書式は機械の対応 G-code の一覧と、実機での確認を根拠にする。

## 既知の制約と、自分で補う部分

policy.md の truck の弱点に対する、設計上の対処を加える(A)。

- panic とハング: 上記のとおり、カーネル呼び出しを隔離する。失敗した入力は回帰テストの資料として保存する。
- STEP: P2 では出力だけを保証し、入力の補強は P5 に回す。基準部品の比較に STEP 入力を使わない(後述)。
- フィレットと面取り: P5 で自作する。Carvera での 2.5D 加工では、内側の角は工具半径で決まるため、P3 までは無くても加工の検証は進められる。

## 検証方針

| 層 | 方法 | 段階 |
| --- | --- | --- |
| コア | 単体テスト。proptest で「取り消し → やり直しで元に戻る」「保存 → 読込で同じ文書」「再計算の結果が毎回同じ」を確かめる | P0〜 |
| 契約テスト | `kmb-contract` に、`Feature` とカーネルが守るべき性質(入力の宣言と実際の参照が一致、エラー時に panic しない、出力の直列化が往復する)を置き、各モジュールが自分のテストで呼ぶ。kmb-core の公開の項目が変わると `cargo xtask verify` がこれを使う crate を全部流す | P0〜 |
| 拘束ソルバ | 答えが分かっている作図(正方形、接円など)の結果と自由度の数を比べる | P1〜 |
| 形状 | ほかの CAD で基準部品を作り、体積・表面積・外形寸法を記録する。同じ部品を本ソフトの CLI スクリプトで作り、許容差内で一致するか比べる。truck の STEP 入力に依存しないよう、その STEP は読み込まない | P2〜 |
| 頑健性 | ブーリアンなどを乱数入力で繰り返し、panic・時間切れを数える。見つけた例は回帰テストに残し、直せたら truck の上流へ送る | P2〜 |
| 経路 | 中間表現の段階で、工具が部品に食い込まない、ストック内で早送りしない、可動範囲内、の検査を自動で行う | P3〜 |
| G-code | insta のスナップショットで、出力の変化を差分として確認する | P3〜 |
| 部品ごと | 変えた crate だけをテストと clippy に掛ける(`cargo xtask verify`)。プッシュの前は依存する側も(`--dependents`)、main へ入れる前は全体を(`--all`)。truck のカーネルでも確かめるのは公開の準備の時だけ(`--all --truck`、2026-10-18 Kie)。手順は docs/verify.md(2026-10-14) | P5〜 |
| ログ | 画面・CLI・MCP は起動ごとにデータフォルダの `logs` へ書く(`log` ファサード、`JC_LOG` でレベル)。クラッシュ報告にログの終わりを添える。レベルの決まりは docs/verify.md(2026-10-14) | P5〜 |
| 加工 | 自前のシミュレーション(高さの格子で削り残しを比べる)→ 空運転(Z を浮かせる)→ 試し削り(ワックスや MDF)の順。試し削りはノギスで寸法を測る | P3〜 |

## 決めたこと

決めたことは docs/機能/ の断片の「決めたこと」に書き、`cargo xtask docs` が target/docs/ に一覧を作る。**この節に行を足さない**(`cargo xtask verify` の点検が落とす)。

## 未決事項

結果を左右するものは、推奨を添えて別途確認する。

- 製品名(policy.md の未決事項のまま)。公開の前まで保留(2026-10-12)。crate の接頭辞は 2026-10-25 に `kmb-` へ変えた。
- P5 の残り: シェル、曲がった辺と曲面の辺のフィレット、STEP で読んだボディの編集。どれを先にするか(2D の負荷一定の荒削りは 2026-10-13 に済み)。
- WASM の戦略を読む口。戦略の入口は `plan(&StrategyInput) -> StrategyOutput`(JSON で往復できる)に全戦略が揃った(構造のレビューの段 4)。WASM の加工戦略は目標に残す(2026-10-21 Kie、構造のレビューの判断 5)。kmb-plugin-host が読むのは今はポストだけ。
- Carvera Air で、手動の工具交換(`M6`)の後に工具長が自動で測られるか。空運転で確かめ、測られるなら `M491` を省く。
- 輪郭加工のタブと、ポケットのらせん・ランプの入り。試し削りの前に要るか、ユーザーの固定方法(両面テープ、クランプ)に合わせて決める。
- 工具ライブラリの既定の工具と切削条件(今は木材・樹脂向けの控えめな仮の値)。ユーザーの手持ちの工具に合わせる。
