# 自作CAD・CAM 方針

kieMonoBench(前の仮の名前は自作CAD・CAM、`jisaku-cadcam`)は、Rust で書くパラメトリック 3D CAD と、Carvera Air 向けの CAM を一つのソフトウェアに統合する。設計したモデルのデータを、そのまま加工へ回せることを最大の強みとする。この文書は決めた方針と、まだ決めていない点を書く。段階計画は別の文書で作る。

## 目的

個人で使える無料の CAD・CAM では、複数のエンドミルを使う加工と、寸法の一覧から調整する機能を使えないことが多く、機械に付く CAM は機能が弱い。そこで、広く使われるパラメトリック CAD に近い操作の流れを持ち、動作が安定して速い CAD/CAM を自作する。

画面の配置・メニューの階層・操作の流れは、広く使われるパラメトリック CAD にそろえる(作業空間の切替、作業空間ごとのタブ付きツールバー、左のブラウザ、下のタイムライン、右の編集パネル、セットアップの下に加工操作を並べる木)。ほかのソフトのアイコン、配色、部品の見た目、製品名・商標は使わず独自にする。ボタン・メニュー・欄の名前は日本語の CAD・CAM で広く通じる語を基本にし、直訳くさい物は普通の日本語にする。長い説明文は自分で書く。言葉は docs/用語表.md にまとめる。特許のある操作部品は作らない。例: 視点の立方体(docs/避ける形.md)。

## 範囲

最初に作るもの:

- スケッチと拘束、寸法パラメータの一覧と、式による調整
- 履歴型(タイムライン)のソリッドモデリング
- CAM のセットアップ、ストック、工具ライブラリ、加工操作
- Carvera Air 向けの G-code 出力

当面作らないもの: T-Spline、5 軸の加工。必要になった時点で、別モジュールとして追加を検討する。

次の物を作る(plan.md「次に作る機能」): 軽い絵(glTF の書き出し、材質と木目、回す動画と削る様子の動画。写真のような静止画まで)、解析(強度と熱 → 流れと空力 → スピーカーの箱)、図面(まず本調査)、ねじ山の本当の形、曲面(サーフェス)と板金(作業平面の後)、レーザー加工、4 軸の加工(後から)。基板(PCB)の加工は作らない。

## 決めたこと

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 作り方 | CAD も CAM も自作する。MIT・Apache・BSD の既存ソフトのコードは、仕組みと値を知るためだけに読んでよい。写さず訳さず、JC のコードは自分で書く(ライセンスの表記が要らない範囲に留める)。GPL・LGPL・AGPL のコードは読まない。ほかの既存実装は設計の参考にとどめる | fork は上流への追従と、上流で追加される機能との分離に手間がかかるため。GPL などのコードを読むと、似たコードを書いた時に写したと疑われるため |
| 言語 | Rust | 速度と安全性。使う予定のライブラリと同じ言語 |
| 構造 | コアと機能を分ける。機能はビルド時に組み合わせる crate とし、ポストプロセッサと加工戦略は WASM のプラグインでも差し替えられるようにする(加工戦略の WASM 化は目標に残す。全戦略の入口は「入力を受け取り経路を返すだけ」の形で、WASM の戦略を読む口はまだ無い)。外部からは CLI と MCP で操作できるようにする | 保守の負担を減らし、複数の箇所の改修を並行して進めるため |
| UI | egui + wgpu。コアと分け、後から付け替えられるようにする。3D ビューは GPU(wgpu)で描き、ソフトウェアの描画装置と安全モードでは CPU の深度つき描画にする(verify.md 7 節) | CAD での前例がある。分離しておけば、Tauri などへの移行も後で選べる |
| 穴の種類 | 単純・ザグリ・皿、止まり穴の底(平ら・ドリルの先、既定 118°)、ネジ(なし・通し穴・ネジ穴)を持つ。ネジ山の形は見た目だけと本当の形の 2 通りを選べるようにする(plan.md「次に作る機能」)。M2〜M12 の並目の表から径(下穴・ISO 273 の通し穴 精・中・粗)とザグリ・皿の既定を決め、属性として残す。ザグリ・皿の値は欄で上書きできる(空なら表)。深さは径いっぱいの部分の終わりまで(先端は含まない)。3D プリンター用のネジ頭の下の段差は後で道具の部品として足す | 広く使われる CAD と同じ分け方。ネジを選ぶとザグリの値を直せない、皿の径が理論の最大で沈みすぎる、という使いにくさは避ける |
| 形状カーネル | SMLib(NVIDIA usd-brep 1.0.0、Apache-2.0、C++)を既定にする。ソースは third_party に置き、cc で静的ライブラリにして C の薄い層から呼ぶ。truck(RICOS、Apache-2.0)も残し、環境変数 `JC_KERNEL=truck` で戻せる。どちらも fork はしない(SMLib は不具合の写しを 2 つだけ当てる)。truck は truck-shapeops の内外の数え方の 1 関数だけを直した写しを当てる(third_party/README.md)。新しい立体の操作は SMLib だけで作り、truck のカーネルでは対応していない誤り(「このカーネルは … に対応していません」)にする | truck はブーリアンが遅く(基準部品 5.9 秒)、フィレット・シェルがない。SMLib は同じ部品を約 0.09 秒で作り、体積の誤差も小さい。CAM・拘束・画面は Rust のまま使える |
| 曲面(面のボディ) | 厚みの無い面だけのボディは、ソリッドと同じく機能の出力 `body` の形で持ち、ソリッドか面のボディかはカーネルに問う(`Kernel::body_kind`)。面のボディの体積・重さ・足し引きは理由つきの誤りにし、STL・3MF・OBJ の書き出しには入れず警告を出す。最初に作るのは「面を張る」と「厚みを付ける」。保存の形は変えない | 保存の形・ボディの続き方・選び方をそのまま使え、面のボディが体積 0 の物として重さや加工へ黙って流れない |
| 解析 | 強度と熱(静的応力・熱・固有振動・軽い形の参考)は自前の kmb-fea で解く。網は形に沿った 2 次(10 節点)の四面体(面の境を保って表面を張り直し、その中を 3 次元の Delaunay で埋めて平たい四面体を直し、辺の中点を曲面へ乗せる。ボクセルと格子から作る作り方は持たない)、解き方は前処理に代数的マルチグリッド(平滑化した集約)を使う共役勾配法と LOBPCG で、網の大きさで直接法と切り替えない(docs/避ける形.md「解析」)。線形・小変形・接触なし。力・応力・温度などの欄は単位を付けない数で、単位は欄の名前に書く(式の単位は長さと角度だけのため)。軽い形の参考は加工の制約を付けない(同)。作業空間「解析」に置く | 外部の解き方や網の部品(GPL の物が多い)を使わずに済み、どんな形でも網が作れる。曲面の形のまま解けるので穴や丸みの応力も表せる。教科書の答えと、曲面の例も含めて 1% 以内で合うことを確かめた(verify.md 10 節) |
| 解析(流れと空力) | 翼は渦格子法(翼のボディの断面から反りの面を読み、馬蹄渦を置く。誘導抗力はトレフツ面、中立点は迎え角を 2 つ解いて出す)。流れは格子ボルツマン法(2D は D2Q9、3D は D3Q19。衝突は TRT と Smagorinsky、壁は Bouzidi の補間つき跳ね返し、入口・出口・横は非平衡の外挿、力は運動量交換)を自前の kmb-flow で、CPU のスレッドで解く。格子で表せない高いレイノルズ数は下げて解き、結果に実際と計算した Re を並べる。面要素の壁・VLES・多孔質の音響は作らない(docs/避ける形.md)。作業空間「解析」の「流れ」に置き、結果の見せ方は強度と熱と共通 | 外部の解き方(OpenFOAM など GPL の物が多い)を使わずに済む。画面の無い CLI・MCP やクラウドの検査でも同じに解ける(GPU は後で速さが要る時に足す)。教科書と標準の問題で確かめた(verify.md 11 節) |
| 対象 OS | まず Windows。macOS と Linux は後で対応する | コアに Windows 専用の API を入れない |
| 順序 | CAD を先に、CAM を後に作る | 統合の強みは、作ったモデルのデータをそのまま加工に使える点にあるため |
| 対象の機械 | Carvera Air を最初の機械とするが、加工の核(セットアップ・工具・戦略・経路)は特定の機械に寄せず汎用に作り、機械ごとの違いはマシンライブラリとポストに閉じ込める。Carvera Air のプロファイルを既定値にする。今の加工の Carvera Air 前提の所も直す。レーザー加工も汎用の仕組みとして作る | Carvera Air に最適化した作りにすると、ほかの機械やレーザーへ広げにくい |
| 機械への出力 | G-code ファイルを出力し、Carvera Controller で実行する | 送信方法は、ポストのモジュールとして後から追加できる |
| 公開 | 公開する予定。ライセンスは MIT と Apache-2.0 のデュアル(決定: 公開の前に決めること) | Rust で一般的な形で、truck などの依存と組み合わせやすい |
| リポジトリ | GitHub の非公開リポジトリに置く。公開時に公開へ切り替える | 端末だけでは故障で失われるため |
| 製品名 | kieMonoBench。アプリは `kie-monobench`、データフォルダは `kie-monobench`(前の `jisaku-cadcam` の中身は最初の起動で写し、前のフォルダは残す)、MCP のサーバの名前は `kie-monobench`。使う人が打つコマンドは CLI が `kmb`、MCP の実行ファイルが `kmb-mcp`(決定: コマンドと MCP の名前を kieMonoBench に)。crate の頭は `kmb-`(決定: crate の頭を kmb- に)。履歴の置き場 `.jc/history`、プラグインの口の名前は変えない(決定: 製品名は kieMonoBench) | 1 単語の名前は検索で既存の物と重なる。使う人に見えにくい名前は、変えると壊れる所が多い割に得が小さい |
| 画面の構成 | 作業空間を「設計」と「加工」に分け、広く使われるパラメトリック CAD と同じ配置と階層にする。ボタン・メニューの名前は docs/用語表.md に従い、アイコン・配色は独自。加工の作業空間ではタイムラインを隠し、セットアップの木で操作を管理する(内部は同じ履歴)。既定の配置は上のとおりで、3D ビュー・ブラウザ・編集パネル・タイムラインはタブを引いて自由に並べ替え・重ね・窓に浮かせられる(部品は egui_dock、MIT)。並びは PC ごとに覚え、表示のメニュー・タブの右クリック・設定で既定に戻す。上の帯・ツールバー・状態の欄は動かさない。窓の帯はアプリが描き(上の帯の右端に最小化・最大化・閉じる)、設定で Windows の標準に戻せる。安全モードは標準の帯。部品はアプリの外の窓(OS の別の窓。別のモニターへも動かせる)にも出せ、閉じると元の場所へ戻り、場所は覚える。外の窓の帯も本体と同じくアプリが描き、本体の中に浮かせた窓も同じ見た目にする。部品を引いて本体の窓の外で離すと外の窓に出す。タイムラインは縦長の所に置くと縦の一覧にする。外の窓は描き直す時を本体と分け、動きの要らない部品で GPU を使い続けない | 今の画面は配置と階層が分かりにくい。この配置は慣れた人が多く、配置やメニューの命令の語と階層は米国の判例で著作権の対象外とされる。短い語句や機能の一般名は著作物になりにくく、長い説明文は著作物になり得るので写さない。見た目と製品名を独自にして、意匠と出所の混同を避ける |
| マウス | 左=選ぶ、右クリック=メニュー、右ドラッグ=回す、ホイール押し=動かす(設定で回すに入替)。回す中心は画面の中心の点で、F・ホイールのダブルクリック・Home・右メニューで置く。形はクリックで決め、押したまま動かす操作は使わない | ドラッグは誤操作する |
| 作る・直す | 選ぶことと直すことを分ける。選んだだけでは値を見せるだけで、直すのはダブルクリック・右クリックの「編集」・パネルの「編集」・Enter で開いた時だけ。新しく作るコマンドは既存の機能を書き換えない。ツールバーで足したものは「作っている途中」で、OK・Enter で決め、キャンセル・Esc で作る前へ戻す(やり直しにも残さない)。クリックで決める流れ(押し出し・穴・フィレット)は、最後の手順をクリックか数字と Enter で決めたらそのまま作り、作っている途中の欄で残りの値を直す(OK・Enter で決める)。穴は 面 → 中心(角・辺の中点・既存の穴に吸い付く)→ 径 で作り、深さ・種類・ネジは欄で直す(径の後にもう一回クリックさせない)。フィレット・面取りは辺か面をクリックで選ぶ(面はまわりの辺すべて)。選ぶ手順・欄は 1 つ選ぶと次の手順・空いた要る欄へ進み、1 つ目に複数を選ぶ時は Ctrl を押しながら選ぶ(後に手順の無い選び直しは足し外しして Enter)。押し出しは押してから輪郭を選べる。Esc は内側から 1 段ずつ戻す。スケッチのできた点はドラッグで動かせる(形を作る時のドラッグ禁止とは別)。スケッチの描く道具は形を作っても続き、使っている道具をリボンで光らせる。寸法は描く途中の欄に打ち、Tab で固定して次の欄へ | 「穴」が既存の穴の位置を流用して書き換えたように見えた。作る命令と編集を分ける |
| 加工画面 | ベッドとネジ穴・L 字の原点を描く。固定具はネジ穴に置き、避ける範囲を経路が避ける。1 つのポケットを工具の順番で削る(順番はユーザーが決める)。入る位置を 3D 上で置ける。G-code は加工とシミュレーションの両方から見る。マシンライブラリを持つ。セットアップごとの置き方と途中の形は案として残す | 既存の CAM の弱い所(複数工具のポケット、入る位置)を使い勝手で上回る。工具の自動選びは作らない(docs/避ける形.md) |
| 加工の高さと空振り | 加工ごとに安全高さ・送り高さ・トップ高さ・ボトム高さを持ち、それぞれ基準(自動・ストックの上面・部品の底面など)とオフセットで決める。自動ならセットアップと戦略の値のまま。加工を選ぶと 3D に 4 つの高さの面を色分けで描く。前の加工(前のセットアップの削り跡を含む)で削った所の空振りは、既定で省いて早送りか下げたままの送りにする(加工ごとの欄「削った所の空振り」で「省かない」にできる)。削った所の判断は「格子の升の全体が工具の中に入った時だけ削れた」とする控えめな高さの格子で行い、触れるか疑わしい所は残す | 既存の CAM の、ストックを見た空振りの削減に合わせる。控えめにして、省いた所で早送りが材料に当たらないようにする |
| 毎回読む資料 | 思想と売り・哲学・構造・入出力の約束・画面と見た目の共通の決まり・作業の決まりの短い形を直下の AGENTS.md に置き、CLAUDE.md から読む。分野の細かい決まりは .claude/rules/ に分け、その分野のファイルを触った時だけ読む。理由と詳細はこの policy.md などの正本に置き、AGENTS.md は節の名前で指す。決まりを変える時は両方を同じ PR で直す。書いた名前・パス・節の実在、大きさの上限、層の表(生成)は `cargo xtask checks` が確かめる | 大きな組み替えでも構想を見失わないため。資料だけの決まりは古くなるので点検で守る |
| 文書の拡張子 | 文書の拡張子は `kmb_core::DOCUMENT_EXTENSION`(開く側は前の物も残す `DOCUMENT_EXTENSIONS`)に集め、字で書かない。公開までは `.json`(決定: 文書の拡張子は公開まで json)。製品名が決まったので `.kmb` にし、前の `.json` も開ける(決定: 文書の拡張子は kmb) | `.jcad` はほかのソフトの拡張子とかぶる。`.kmb` は古い計測の道具のデータで使われていた程度 |
| 辺を拾う | 3D のビューで辺を拾う道は CPU の 1 本(隠れは面の箱の木で辺の上の点ごとに見る)。GPU の番号の絵は使わない(決定: 辺を選ぶやり方を 1 つにそろえる) | PC(GPU の有無)によって選ばれる辺が変わらないようにする |
| 奥の線 | 本体に隠れたスケッチの線と作業平面は、手前に見える所を今の線のまま、隠れた所を隠れた辺と同じ刻みと濃さの薄い点線で描き、作業平面の塗りは手前に見える所だけにする。表示の「全部透かす」(既定は切)で全部を形の上に重ねる。線だけの表示では全部を描く(決定: 本体の奥のスケッチを点線で) | 奥にある事と、どこまで続くかの両方が見え、どれが手前かを取り違えない |
| 見本 | 見本の文書(基準部品とその加工など)はアプリに組み込む。中身は kmb-samples でコードから組み、文書のファイルを置かない。利用者に見せる見本は組み立ての一覧 `kmb_bundle::Sample` に足し、画面の `--sample`・CLI と MCP の `sample`・画面の試験は、その一覧から同じ見本を使う。見本を組む部品(`DocBuilder`・`SketchBuilder`)は見本と試験で共有する。見本を足したら、開いて再計算が通る試験を足し、地図「見本」に書く。機能ごとのチュートリアルはこの作り方を流用して後で作り(決定: 機能ごとのチュートリアル)、発展形の見本は組み込まず後から落とす形を考える(決定: 見本を後から落とす) | 見本は良い物なので組み込んだまま残し、置き場所と管理を決めておく。コードで組めば保存形式が変わっても見本が古くならず、試験と同じ物を見せられる |

## 構造の考え方

コアは小さく保ち、変更をなるべく少なくする。コアが持つのは、文書モデル、タイムラインと依存関係の再計算、パラメータと式、コマンドの登録と取り消し、イベント、形状カーネルの接続口、保存形式である。コアの API は、変えると全モジュールに影響が出る。そのため公開の項目の一覧を検査で見張り、変わったら全モジュールの契約テストを流して互換性を守る。版の番号(`CORE_API_VERSION`)は公開まで上げない(読む物が無く、上げると取り込みの衝突の元になるため)。

機能モジュールは次のように分ける。

- CAD: スケッチと拘束ソルバ、ソリッド操作、形状カーネル(SMLib・truck)への接続、STEP と STL の入出力
- CAM: セットアップとストック、工具ライブラリ、加工戦略(差し替えの単位は戦略の名乗り〈`module()` が登録する 1 戦略〉。crate は加工の種類のまとまりにし、レーザーは分ける)、経路の中間表現、シミュレーション、ポストプロセッサ
- UI: 画面の枠組みと 3D ビューポート

画面は機能の名前を書かない。特定の操作・種類・設定を探す時は、役割の印(`ActionRole`・`KindRole`・`SettingsRole`)で探す。印の型はコアに、語彙(押し出し・機械など)は kmb-interchange の `role` に置き、モジュールが名乗る。画面が要る計算(押し出す道具の下絵、面の縁の輪郭など)は機能が持ち、拡張点(手順の形、重ね描き、記述子の直し方の例)から渡す。コアに個々の機能の幾何を置かない。

各モジュールの crate は `module()` で 1 つ名乗り(登録する種類と操作)、組み立て(kmb-bundle)がそれを 1 回ずつ並べる。加工戦略の名乗り(ボタン・まとまり・初めの値・入る位置・荒削りの格子・残り削りの工具・底の面の足し外し・工具の順番・部品の切り抜き)はデータで、加工の操作は戦略の名前を知らず、戦略の crate にも依存しない(テストを除く。xtask の層の点検が落とす)。戦略の計算は、ホスト(加工の機能の evaluate)が式・参照・網を解いた入力 `kmb_cam_setup::StrategyInput` だけから経路を作る純関数 `plan` にし、戦略はカーネルに触らない(入力と出力は JSON で往復でき、WASM の戦略と同じ入口になる。全戦略がこの形)。機械とポストの選択も組み立てが決める。CAD と CAM の間で受け渡す型(穴の情報など)は、コアでなく受け渡しの部品 kmb-interchange に置く。CLI・MCP も操作を役割の印で探す。スケッチの付属の機能(文字 kmb-text、DXF kmb-io-dxf、SVG kmb-io-svg)もそれぞれのモジュールで、スケッチ(kmb-sketch)の型と操作の部品(`selected_sketch`・`insert_file`)を使う。別のモジュールの操作のまとまりの中に並べる操作は `Action::before` で置き場所を名乗る。拘束ソルバの数値の部分(式とその解き方)は kmb-sketch-solver に置き、作り直しはそこで新旧を切り替えて比べる。

重ね描きの線と箱は、描き方の役割(`LineInk`・`BoxInk`。主の線・移る線・薄い参照の線・作図の線など)と凡例の名前で渡し、画面は役割だけで色と破線を決める。加工の経路や機械の線といった分野の種類をコアに置かない。再生の帯で出す・隠す線も、モジュールが名前と役割で渡す。

戦略の crate が持つ操作(穴あけの「穴から加工を作る」など)は、戦略の名乗りに付けて渡し、加工の操作が自分の操作と同じ所に並べる。タブを置く・削る輪郭を選ぶ手順を使えるかも名乗りのデータで示す。工具の動きの部品(入り方・リード・仕上げの周回、輪郭に沿う動き、経路のつなぎ)は kmb-toolpath-moves に置き、kmb-cam-setup は同じ名前で再公開する。kmb-solid は CAD の機能を全部通した試験だけの crate で、見本の組み立ては kmb-samples に置く。

加工戦略は、形状への参照と工具とパラメータを受け取り、機械に依存しない中間表現(移動、円弧、工具交換、主軸の指示)を返す。ポストプロセッサは、その中間表現を G-code に変換するだけにする。戦略と機械を別々に追加できるようにして、機械に付く CAM のような機能の制約を避ける。

CAD を先に作る場合でも、次の二つは最初からコアで扱う。後から入れるのは非常に難しいためである。

1. 参照の永続化。形状を作り直しても、加工操作が参照する面や稜線を追跡できるようにする。
2. CAM の操作も、CAD と同じタイムラインと依存関係の再計算に載せる。寸法を変えると、加工経路も作り直されるようにする。

## 使い勝手の原則

ファイルはローカルが正で、ネット接続を必要にしない。画面をモーダルにしない。保存した設定や古い形式のせいで起動できなくしない(読めなければ既定で起動し、形式は変換して元を残す)。新しい機能や画面は、評判の良い既存ソフトの使い勝手と問題点を調べてから設計する。画面の配置と階層は広く使われるパラメトリック CAD にそろえ、アイコン・配色・見た目は独自にする。ボタン・メニュー・欄の名前は日本語の CAD・CAM で広く通じる語を基本にし、直訳くさい物は普通の日本語にする。ボタンとラベルは一言、説明は文脈の無い人にも何が起こるか分かるよう短く自分で書く(docs/用語表.md)。ほかのソフトの画面のコードは取り込まない。

## 依存とライセンスの扱い

GPL と LGPL のライブラリは依存に使わない。usd-brep の中では、LGPL の部品を使う部分(STEP の読み書き)と開発用 GUI が該当する。使っている依存の正本はルートの Cargo.toml の workspace.dependencies で、ライセンスは deny.toml で検査する。初めの候補のうち Clipper2 と manifold は使わなかった(2D の重なりは i_overlay、ストック除去シミュレーションは自作の高さの格子)。

ほかのポストのコードは流用しない。MIT・Apache のコードは仕組みと値を知るためだけに読み、写さず訳さない(「決めたこと」の作り方)。truck の 1 関数を直した写し(third_party/README.md)は認めた例外。

## 既知の制約と、自分で補う部分

truck には次の弱点がある(上流の issue による)。既定のカーネルを SMLib に替えたので、truck は戻すための控えと、SMLib の読み手で組めない STEP の読み込みに使う。

- フィレットと面取り、シェルとオフセットの機能がない。自分で実装する。
- ブーリアン演算で panic やハングが起きる例があり(#135)、面が重なる形状の扱い(#114)と速度(#68)にも課題がある。
- STEP の入出力で、変換の誤りや panic が起きる(#123、#128、#132、#133)。補強が必要になる。
- デバッグ用のアサートが、正しい形状を拒否することがある。

修正できたものは truck の上流へ送り、手元に差分を抱え込まないようにする。

SMLib(usd-brep 1.0.0)の制約:

- 上流 1.0.0 のブーリアンは解放済みのメモリに書き込む。smlibpy(MIT)の修正の写し 2 つ(third_party/smlibpy-patches)を当ててビルドする。
- STEP の読み書きは LGPL の部品経由しかないので使わない。書き出しは smlibpy の書き出しを C++ に移したもの、読み込みは自前の読み手(kmb-kernel-smlib の step_in)で、組めない物は truck に任せる。
- SMLib は 1 つの文脈を全体で共有するので、呼び出しは 1 本の錠で 1 スレッドずつにする。

## Carvera Air への出力仕様(調査結果)

- ファームウェアは Smoothieware の派生版である。コミュニティ版ファームでは G20(インチ)が停止扱いになるため、mm 単位で出力する。
- 工具交換は `T<n> M6` で指示し、交換を促す表示は機械側が出す。手動交換後に工具長を自動で測り直すかは、純正ファームの文書では確認できていない(未確認)。
- コミュニティ版ファームでは、M6 に工具長やコレットを指定するパラメータが追加されている。
- レーザーは `M321` でレーザーの工具に替え、焼く送りの行の `S` に 0〜1 の出力を書き、`M322` で戻す(機械の対応 G-code から。実機では未確認、A)。
- 表面の高さの補正は、先頭の `G32 R1 X Y A B I J H`(範囲の始まり、幅と奥行き、点の数、測る高さ)と、終わりの解除 `M370` で書く。R1・I・J・H の正確な意味は実機で確かめていない(U)。

## 機械とポスト

- 機械はセットアップごとに選ぶ(`machine`。欄の無い古い文書は `carvera-air`)。セットアップは足した時の機械の値(設定で直した値を含む)を文書に写して持ち(`machine_values`)、経路の計算・検査・ポストは同じ写しを使う。設定の画面の機械の値は、新しいセットアップの初めの値だけになる。機械とポストの一覧(マシンライブラリ、`kmb_post::machines::MachineLibrary`)は組み立て(kmb-bundle)が決める。Carvera Air の値は kmb-post-carvera-air、汎用 3 軸の Fanuc 系・Grbl 系と SCULPFUN G20 は kmb-post にある。汎用の加工の crate は機械を名指ししない(xtask の点検)。
- 作業座標系の数、O 番号、任意停止、レーザーの命令、高さの補正の命令、1 段の深さの表は、機械の値に持つ。加工の核(セットアップ・工具・戦略・経路)はこれらを機械の値から読み、Carvera Air の名前や命令を持たない。
- 内蔵のポストは Carvera Air と汎用(Fanuc 系・Grbl 系)と、LightBurn に取り込む SVG。動きの行の書き方は kmb-post の `writer` を共有する。プラグインのポストは今までどおり作業座標系を自分で決めてよい(内蔵のポストだけが機械の作業座標系の数で確かめる)。
- レーザーは工具の種類「レーザー」で表す。切削条件の回転数の欄を出力(%)、送りを速さとして読み、主軸は回さない。焼かない送り(焦点の高さへ下りる所、塗りの行の外のはみ出しと行の間)は出力 0 で書く。
- レーザーで切り抜く: 工具の径を切り口の幅とし、レーザーの工具の既定は 0.01 mm。補正は経路で済ませる(コンピュータ側のみ。G41/G42 は Grbl と Carvera が持たない)。閉じた線を偶奇の規則で内外を決めてずらす(部品を残す: 外周は外・穴は内)。進入・退出(直線か 1/4 円)は捨てる側、焼き始めは最も長い辺の中ほど。重ね切りは最後の回だけ。貫通は焼き始めで止まったまま焼き、止まって焼く命令は機械の値に持つ(Grbl は M3 に替えて G4、Carvera Air は動く間だけ焼くので誤りにする。A)。
- ガルバノのレーザー: 機械の値のレーザーに駆動の種類(軸・ガルバノ)を持つ。ガルバノでは塗りのはみ出しを 0 にする。SCULPFUN G20 は G-code で動かず LightBurn(Pro)が動かすので、書き出しは LightBurn に取り込む SVG(ポスト `lightburn-svg`、拡張子 .svg)。焼き始め・終わり・角の遅れ(TC)とレンズのゆがみの補正は LightBurn の機械の設定に任せ、こちらでは持たない(二重に補正しないため)。直接動かすか、ウォブル・回ごとの Z の下げを足すかは、実機で確かめた後に決める。
