# Issue と PR の受け方

外から届く Issue と PR を、維持する人がどう仕分けて返すかの決まり。ラベルの定義は `.github/labels.yml` が正本で、ひな型(`.github/ISSUE_TEMPLATE/`)が付けるラベルはそこに無いと点検(ラベル)が落とす。GitHub への反映は `cargo xtask labels` が出す `gh label create` のコマンドを維持する人が流す。

## ラベルの使い分け

| ラベル | 付ける時 | 付けるのは |
|---|---|---|
| bug・enhancement・question・machine | 届いた物の種類 | ひな型が自動で付ける。空の Issue には読んだ人が付ける |
| safety | 誤った G-code・機械の動く範囲の外へ出る経路など、機械や人を傷つけうる物 | 読んだ人。題に「G-code」とある物は必ず見る |
| needs-info | 再現や判断に要る情報を聞いた | 聞いた人 |
| confirmed | 不具合を再現できた、または作ると決めた | 確かめた人 |
| duplicate・wontfix | 閉じる理由 | 閉じる人。理由と行き先を返事に書く |
| good first issue | 1 つの crate の中で済み、設計の判断が要らない小さな物 | 維持する人 |

種類のラベルは 1 つだけにする。状態のラベル(needs-info・confirmed)は、状態が変わったら付け替える。

## 読む順

1. safety の物を先に読む。再現できたら、直すまで README の「できないことと予定」か使い方の注意に書く。
2. 脆弱性が公開の Issue に書かれていたら、中身を引かずに SECURITY.md の非公開の報告へ移ってもらい、Issue は閉じる。
3. ほかは届いた順に読む。返事の早さは約束しない。

## 返し方

返事は相手の言葉(日本語か英語)で書く。ひな型どおりの文で済ませず、その Issue の中身に 1 文は触れる。

| 場面 | 返す中身 |
|---|---|
| 受け取った | 読んだこと、再現できたかどうか、次に何をするか |
| 情報が足りない | 足りない物を箇条書きで聞き、needs-info を付ける。30 日返事が無ければ、また開けることを書いて閉じる |
| 再現できない | 試した手順と版を書き、needs-info を付ける |
| 同じ物がある | 先の Issue へのリンクを書き、duplicate を付けて閉じる |
| 作らない | 理由を書き、wontfix を付けて閉じる。理由は思想(AGENTS.md)・ライセンス・作らない形(docs/避ける形.md)のどれに当たるかで書く |
| 機械の追加 | 機械の値はマシンライブラリに足す。ポストを足すのは G-code の方言が違う時だけ。動いた G-code の例が無い時は needs-info |
| 質問 | 答えを書き、docs/使い方.md に無い答えなら使い方に足す |

作らない時も、困り事の意図は汲む。同じ困り事を別の形で解けるなら、その形を返事に書き、新しい Issue にする。

## PR の受け方

- 作る前に Issue で相談していない大きな PR には、Issue で目的を相談してから進めるよう返す。閉じはしない。
- 本文に検査の件数(通過・失敗・飛ばし)が無ければ聞く。点検が落ちていたら、点検を緩めず直すよう返す。
- GPL・LGPL・AGPL のコード、ほかのソフトから写したコードは受けない。疑わしい所は出どころを聞く。
- コミットの説明・PR の本文・ブランチ名に他製品の名前が入っていたら、働きで書き直してもらう。取り込みの点検(他製品の名前)はコミットの説明も見る。
- 外から届いた PR は自動では取り込まない。検査(GitHub の CI)が通り、維持する人が変更の中身を読んで受けると決めてから、GitHub の画面で merge commit で入れる。自動で入るのは、このリポジトリ自身の作業のブランチから持ち主が出した PR だけ(docs/verify.md の 16 節)。

## 名前とロゴ

製品名とアプリのアイコンは、コードのライセンスの外に置く(TRADEMARKS.md)。名前やアイコンを使ってよいかの問い合わせは、TRADEMARKS.md の範囲で答え、範囲の外は個別に答える。
